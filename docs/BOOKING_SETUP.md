# 狐隱 KOGAKURE｜即時狐姬指名預約（2026-11-14）

## 介面

- 前台 `/booking`：直接沿用已公開的「狐姬」名帖照片與姓名（不包含「婆婆」「星詠」等非狐姬職稱）。
- 狀態：**綠色空閒中**＝目前未被接取的有效指名占用；**紅色指名中**＝已有管理員接取的指名，尚未到達方案截止時刻。
- 點角色卡會開啟表單：**FFXIV 角色姓名、伺服器、指名方案、是否加選其他狐姬（最多合計四位）、備註（選填）**。
- 送出只是待審核申請。任何一位指定狐姬已忙碌時，後台不可接取整組申請；會提示重新安排。
- 完成接取的時間戳來自 Supabase 資料庫，不使用旅人的電腦時鐘當起始時間。多位狐姬同組時共用同一方案、起始和截止時刻。
- 管理後台 `/admin/booking`：待審核、指名中、已完成、已婉拒，完整資訊檢視、接取／婉拒／提前結束，以及方案新增／修改／上下架。
- 管理員在任何後台頁面都會看到待審核提示，新的申請會顯示名稱／伺服器／方案；管理頁保持開啟時可透過 Realtime 或每 7～9 秒輪詢取得變更。
- 倒數計時在後台依 `ends_at` 即時顯示。到期後前台會自動恢復綠色空閒中；後台仍保留「指名中／待結案」記錄，直到管理員按「結束服務」，以免遺失歷史處理資訊。

## 正式方案與價格：需要館方審核

資料庫只建立兩個**未啟用**的範例：`狐姬指名・30 分鐘`、`狐姬指名・60 分鐘`，費用皆為 **NULL／未設定**，不代表已核准的收費規則。

1. 先用既有管理員登入 `/admin/booking`。
2. 切換「指名方案管理」，逐一修改方案名稱、時長、內容與 Gil 費用（可留空）。
3. 確定後勾選「對旅人開放此方案」並儲存。
4. 前台才會顯示可選擇方案並允許送出申請。

## Supabase

Migration 路徑：`supabase/migrations/20261114_01_booking.sql`。

建立四個表（皆啟用 RLS）：

- `booking_plans`：可以公開的啟用方案；只有管理員能編修。
- `booking_requests`：角色姓名、伺服器、方案快照、狀態、接取／結束時間，**訪客不可讀或寫此表**。
- `booking_request_staff`：每張申請對應的狐姬，**只有管理員可讀**。
- `staff_booking_presence`：只公開狐姬 ID 及忙碌截止時刻，不公開客人名稱、預約 ID、方案等私人資訊。

公開表單只能呼叫受嚴格驗證的 `submit_booking_request` RPC，匿名不能直接 INSERT 或 SELECT 申請內容。此 RPC 為刻意允許公開執行的狹窄 `SECURITY DEFINER` 寫入入口，具備長度限制、同一姓名／伺服器 10 分鐘內禁止重複待審核、每小時待審核流量保護；這些是基本防濫用措施，**不等同 CAPTCHA、WAF 或 IP 節流**。若正式營運出現大量濫用，應搭配 Cloudflare Turnstile / Edge Functions 與速率限制。

管理員透過 `decide_booking_request` `SECURITY INVOKER` RPC 進行原子操作，驗證 `is_site_admin()`，在資料庫交易中鎖住預約與狐姬狀態列後接取，不會讓同一位狐姬同時被兩張有效預約占用。重複接取與跨管理員競爭會被資料庫拒絕。方案一旦被提交，申請會保存當時的名稱、時長與價格，不受後續方案編輯影響。

## 上線流程

1. 確認已經備份正確的狐隱 Supabase 專案，且沒有與新四個表衝突的既有結構。
2. 套用 migration，檢查四個表及函式、RLS、匿名表權限；本專案與人員／茶宴共用同一個 publishable key。
3. 核對 Realtime `supabase_realtime` publication 包含 `booking_requests`（僅管理員可以查看）及 `staff_booking_presence`（不含訪客隱私）；即使未訂閱成功，畫面仍會定期輪詢狀態。
4. 發布 GitHub Pages，確認 `/booking` 與 `/admin/booking` 直接連結可用；確認所有原有名帖、茶宴及服務頁面不受影響。
5. 先在後台開放一個已審核方案，從另一個無痕視窗測試**送出 → 後台接取 → 狐姬變紅 → 開始計時 → 結束服務 → 狐姬變綠**。
6. 使用匿名角色檢查 `booking_requests`、`booking_request_staff` 無 SELECT 權限；試圖直接 INSERT / UPDATE 皆遭拒絕。
7. 同時從不同管理頁面接取含相同狐姬的兩筆待審核申請：只能有一筆成功，另一筆應顯示忙碌錯誤。

## 隱私與限制

- 目前不收集真實姓名、電話、Email 或帳號密碼，僅收集 FFXIV 角色姓名、伺服器、方案、所選狐姬及可選備註。
- 後台只有原本已授權 `admin_users` 的管理員可開啟；不提供匿名查詢別人的預約狀態或內容。
- 新預約通知是**管理頁開啟期間**的即時提示與輪詢；頁面關閉後不會自動寄信或推播。
- 現階段是**即時指名接取**，不提供未來日期／時段排程、付款、取消連結、Discord 通知或顧客登入。
- 歷史預約有外鍵關聯，為防資料遺失，具有預約紀錄的狐姬不可直接刪除；如需離職可先改成未公開。

## 2026-11-14｜獨立預約顯示、橫式指名名片與後台增刪

- 於 `/admin/staff` 編輯每位狐姬時，可獨立設定「**在狐姬預約頁面顯示**」。這個開關不影響 `/staff` 的一般名帖公開狀態；實際出現在預約頁的條件為 **名帖已公開 + 職稱包含「狐姬」 + 預約顯示已開啟**。
- 既有員工的 `is_booking_visible` 預設為 `true`，上線不會忽然隱藏所有原有的狐姬。關閉後無法提出新指名，已開始的接待紀錄、計時和狀態仍保留至服務結束。
- `/booking` 改用 **橫向長方形** 名片：左側獨立角色照片、右側文字資訊與綠／紅狀態。照片與文字不再彼此覆蓋，繼續保留之前由後台手動選擇的名冊裁切範圍。
- 新的 `/admin/booking`「**新增預約**」可填寫遊戲角色姓名、伺服器、指名方案（含尚未公開的後台方案）、一至四位狐姬及備註。建立後一律進入待審核；**不會自動接取或開始計時**。
- 在預約列表或詳細資料頁可「**刪除**」。管理員必須輸入「刪除」再確認永久刪除。若刪除指名中的申請，資料庫會在交易中只釋放該筆預約占用的狐姬，不會清除其他後續接待的狀態。
- 資料庫 migration：`supabase/migrations/20261114_02_booking_cards_admin_crud.sql`。僅新增 `staff.is_booking_visible` 欄位、更新既有預約提交／接取 RPC 的顯示檢查，並新增 admin-only 建立／刪除 RPC 與必要的 RLS 權限。**不會刪除或重置既有預約／員工資料**。
- 管理員建立、刪除都必須透過具備 `is_site_admin()` 授權檢查的 SQL RPC。訪客仍不得讀取其他旅人資料，也不能刪除申請。刪除為不可回復的管理操作；如需留存歷史建議先備份。

### 變更後必測

1. 後台關閉一位狐姬的預約顯示後：名冊仍可看到人員，但預約名片不再出現。
2. 開啟顯示後：預約名片可看到左側照片、右側文字與狀態。
3. 後台手動建立一筆待審核預約，確認接取前綠色、接取後紅色與方案倒數。
4. 對指名中的申請輸入「刪除」：紀錄消失，狐姬狀態恢復（同時不影響其他活躍接待）。
5. 匿名／非管理員無法執行 `admin_create_booking_request` 與 `admin_delete_booking_request`。

## 2026-11-14｜預約名片可變高度與不限職稱的指名

- 橫式名片已改為**自動依文字高度延伸**；左側獨立照片、右側姓名、職稱、狀態、短句、服務標籤與操作提示。取消固定 282px 高度及造成文字遮擋的規則，文字換行時不會被截掉，手機尺寸也依內容增高。
- 名冊照片若已由管理員手動圈選，預約名片將使用 `object-fit: contain` 保留完整圈選構圖；為避免裁切，在較高的名片上可能出現適當留白。
- **可指名資格不再限定職稱含「狐姬」**。只要人員名帖已公開（`is_published=true`），且後台「在預約頁面顯示並接受指名」（`is_booking_visible=true`），任何職稱都可以出現在預約名片與後台手動新增的選擇清單。
- 後台開關仍可針對個別員工關閉，原本的人員名冊顯示與既有指名計時不受影響。
- 新 migration：`supabase/migrations/20261114_03_booking_all_roles.sql` 只更新前台申請、後台手動新增及館方接取三個 RPC 的職稱限制，不刪除資料、改動價格或放寬非管理員存取預約資料的權限。

驗收：分別測試「婆婆」、「星詠」與「狐姬」名帖在開關開啟時能被指名，關閉時不能指名；輸入長職稱、長姓名與多行短句，確認預約名片不會截斷文字。

- 若尚未啟用任何指名方案，名片仍可點選查看預約視窗與角色資料；表單清楚標示「尚未開放」，並禁止送出，直到館方啟用方案。不會偷偷建立任何預約。
