# 狐隱 KOGAKURE｜指名預約變更與必要性

本文件以 **2026-11-17** 的規則為準。過去版本的「僅限狐姬職稱」「最多四位指名」「姓名須 2～48 字」已被後續變更取代，不再作為現行規則。

## 已完成變更

| 項目 | 目前規則 | 必要性 |
| --- | --- | --- |
| 指名資格 | 名帖已公開且 `is_booking_visible=true`；不限制職稱 | 區分一般名冊與是否接受指名 |
| 開關權責 | `booking.manage` 控制可指名性；名帖編輯不覆寫該欄位 | 避免跨模組儲存互相還原設定 |
| 指名人數 | 主要 1 位、追加至多 1 位，總數最多 2 位 | 避免表單與資料庫規則不同步 |
| 遊戲世界 | 繁中服七個世界選單 | 減少自由輸入錯誤 |
| 角色姓名 | 取消舊版 2～48 字限制；仍拒絕空白及控制字元 | 兼容較長角色名稱，但增加資源耗用風險 |
| 預約名片 | 橫式照片與文字分區、可變高度、狀態可見 | 避免圖片遮住文字及長內容截斷 |
| 方案 | 只有經館方核定且啟用的方案才可公開 | 不把範例價格誤認為正式收費 |

## 資料與權限變更

- `booking_plans` 保存方案；`booking_requests`、`booking_request_staff` 保存非公開申請及指名關聯；`staff_booking_presence` 僅公開必要的忙碌狀態，不揭露旅人資料。
- 公開申請透過受控 `submit_booking_request` RPC；後台接取透過資料庫交易與鎖定檢查，避免同一館員同時被兩筆有效指名占用。
- 方案名稱、時長與價格在申請時保存快照，避免後續修改影響歷史訂單。
- 已建立的申請不因指名開關關閉而自動取消；預約刪除與拒絕是不同資料操作，永久刪除有不可回復風險。
- `booking.manage` 並不授予整張名帖的任意 UPDATE；匿名者不得直接讀取私人申請，也不能直接修改接取狀態。

## 尚存風險及必要性

- 目前公開表單的同名／世界冷卻規則不足以取代可信來源的 IP／網路限流及防機器人措施。
- 已移除姓名長度上限，仍需決定合理請求大小限制，降低惡意超長內容造成的成本。
- 資料庫 RLS、授權委派、同時接取競爭及 Realtime 退化為輪詢的情況仍需要正式環境驗證。
- 預約只處理即時指名，不包含未來時段預約、金流、旅人登入或通知外送；任何擴充都須重新評估隱私和交易一致性。

## 預約專用形象照片（2026-11-23）

- 前台指名卡片與指名視窗改讀 `booking_staff_photos`，不再直接引用員工名帖的圖片欄位。
- 既有名帖的縮圖／原圖在資料庫升級時**只複製 URL 作為預約初始照片**，不搬移或覆寫實體圖片，保持目前的視覺外觀。
- 後台「預約管理 → 可指名人員設定」新增每位人員的獨立圖片上傳、更換與刪除，操作後即儲存，不必另按預約方案儲存鍵。
- 刪除預約圖片會改顯示預設佔位圖，**不回填名帖圖片**；既有員工名帖及值班照片均不受影響。
- 新上傳圖片儲存在 Supabase Storage 的專用 `booking-media` 公開 bucket，轉成 WebP，原始比例保留，長邊至多 1200px，來源不可超過 12MB。
- 獨立表格與儲存權限由 `supabase/migrations/20261123_02_booking_staff_photos.sql` 建立：只有具備 `booking.manage` 的管理者可上傳／替換／刪除，匿名者僅可讀取已公開且開放指名館員的預約照片。
- **發布順序：先套用 Supabase migration，再合併前端 PR 發布 GitHub Pages。** 同步測試前台圖片、無圖狀態、後台圖片替換與刪除、未授權拒絕、名帖／值班圖片保留、手機版。
