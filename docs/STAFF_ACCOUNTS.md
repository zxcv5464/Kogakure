# 狐隱 KOGAKURE｜員工登入帳號與權限管理

## 使用方式（免寄送郵件）

1. 正式管理者使用既有管理員帳號登入 `/admin`，進入左側「員工帳號」或直接開啟 `/admin/accounts/`。
2. 點選 **新增員工帳號**，填寫員工顯示名稱、專屬登入帳號與初始密碼（兩次相同）。
3. 勾選所需權限，按「建立員工帳號」，由管理員以安全的方式私下提供員工帳號及初始密碼。**不會寄出任何員工邀請、確認或重設密碼郵件。**
4. 員工使用 **帳號名稱＋密碼** 登入 `/admin/`；正式管理員則繼續用既有 Email＋密碼登入。
5. 點選左側員工，可變更顯示名稱、後台權限、啟用狀態，也能直接 **重設員工密碼**。若為舊版 Email 邀請建立的帳號（顯示「舊版員工帳號」），則透過「舊版帳號轉換」設定新的登入名稱及密碼，保留原本帳號身分與後台權限，不會自動刪除。
6. 點選「永久刪除帳號」時，必須正確輸入員工的登入帳號並再次確認，才會刪除登入身分與授權；**不會刪除名帖、菜單和歷史預約**。

## 帳號與密碼規則

- 登入帳號：3～24 位，英文字母開頭，其餘為英文字母、數字、底線（`_`）或連字號（`-`）；英文不分大小寫。
- 密碼：12～128 個字元，包含至少一個英文字母與一個數字。管理員必須輸入兩次以確認。
- Supabase Auth 只能使用電子郵件或電話作為密碼認證識別，因此後台**僅在內部**將自訂帳號映射到固定的保留識別地址（`帳號@staff.kogakure.invalid`），不需要員工提供真實 Email、不會使用此地址發信。
- Supabase Auth 只儲存密碼雜湊，**不會把原始密碼寫入 `employee_accounts` 或展示在帳號管理列表中**。管理員忘記原密碼時須重設，無法查看舊密碼。
- 管理者的既有 Email 登入方式維持不變；正式管理者本人的帳號不在「員工帳號」刪除範圍內。

## 員工登入後自行修改密碼

- 使用員工登入帳號＋密碼進入 `/admin/`，在 **「管理總覽」→「我的帳號安全 · 自行修改密碼」** 直接設定新的密碼，無需 Email、管理員介入或 Edge Function。
- 必須輸入 **目前密碼**，並將新密碼輸入 **兩次**。新密碼與管理者建立員工帳號時使用相同規則：12～128 字，包含英文與數字，且不可與目前密碼相同。
- 系統從目前登入的 Supabase Auth 身分取得本人 ID 與內部登入 Email；以獨立、**不儲存 Session** 的驗證客戶端確認目前密碼及同一個 Auth ID，接著透過已登入使用者的 `auth.updateUser({password})` 只修改**自己**的密碼，不會修改任何員工的功能權限或管理員帳號。
- 修改成功後清空所有密碼欄位，並提示下次登入使用新密碼。網站不儲存原始密碼，也不會傳送密碼通知郵件。
- **忘記目前密碼** 無法在員工端自行略過驗證，須聯絡管理員在「員工帳號」管理頁重設。管理員仍可繼續使用原本的帳號安全設定功能。

## 權限表

| 功能 | 正式管理員 | 可授予員工 |
| --- | --- | --- |
| 員工名帖 | 全部 | `staff.manage`：名帖、照片、順序、公開狀態 |
| 茶宴菜單 | 全部 | `menu.manage`：分類、品項、金額及供應 |
| 預約管理 | 全部 | `booking.manage`：預約審核、方案、計時及歷史 |
| 員工帳號與權限 | 全部 | **不能授予** |

每個權限包含相應模組的管理／編輯操作，不是唯讀模式。前端僅顯示已授權模組，PostgreSQL RLS 和受控 RPC 也會拒絕沒有權限的人員。

## 刪除與停用的差異

- **停用**：保留登入帳號、設定與歷史資料，但資料庫立即拒絕該員工的後台存取；可重新啟用。
- **刪除**：從 Supabase Auth 永久刪除該員工的登入身分，`employee_accounts` 經外鍵 `ON DELETE CASCADE` 自動移除對應授權。無法還原密碼或身分。重新聘用需新增新的登入帳號。
- `staff` 名帖表、`menu_items` 茶宴、`booking_requests` 預約及預約人員關聯表**沒有以員工帳號 ID 為刪除依據的外鍵**，不會因為刪登入帳號而被刪掉。
- 刪除 Auth 使用者後，先前核發的 JWT 可能尚未到期；但授權資料已刪除，RLS 會立即拒絕私有資料存取。管理員重設密碼後，員工現有瀏覽器 session 未必立即登出。如需強制中止資料存取，先停用即可。

## 部署及驗證

- 原先的 `supabase/migrations/20261115_01_employee_accounts_permissions.sql` 等資料庫保護規則保留。
- 新增 `supabase/migrations/20261115_04_employee_usernames.sql`，為員工登入增加唯一的 username 欄位。舊版已存在的員工帳號會暫以 `legacy_...` 識別，**仍可沿用原有 Email 登入，直到管理者選擇轉換**；新建員工帳號的 Auth email 欄位僅作內部登入識別。
- 重新部署 `supabase/functions/manage-employee-accounts/index.ts`，保持 `verify_jwt=true`。只允許正式管理員、使用伺服器端金鑰呼叫 `auth.admin.createUser`、`updateUserById` 和 `deleteUser`，瀏覽器不可取得 service-role key。
- GitHub Pages 發布後，管理者可使用真實員工帳號驗收建立、登入、修改權限、重設密碼及刪除，並確認歷史名帖和預約資料不變。
- 不額外建立假員工或寄信測試，不改原始正式管理員帳號。

## 補充

員工帳號仍由管理者建立，不開放自助註冊或忘記密碼時的自助找回；**已登入且知道目前密碼的員工可以自行修改自己的登入密碼**。員工不能修改其他帳號或提升正式管理者權限。
