# 狐隱 KOGAKURE｜茶宴菜單變更與必要性

## 已完成變更

- 前台「狐之茶宴」有茶飲、和菓、御膳三個初始分類及十一項種子品項；正式內容由 Supabase 已發布資料決定，不以種子資料視為營運定價。
- 已發布分類與品項對訪客可讀；暫停供應品項不可提交。前端可計算 Gil 合計，正式送單由資料庫重新驗證價格與供應狀態。
- `menu.manage` 只控制菜單分類、品項、價格與供應；`orders.manage` 為獨立的訂單權限，減少無關人員接觸旅人資料。
- 缺少正式資料來源時可能使用標示清楚的只讀展示資料；**展示模式不代表成功連線，也不能產生正式訂單**。
- 菜單編輯加入更新時間比對以降低多人編輯覆蓋風險；已有品項關聯的分類受到資料庫刪除限制。

## 為什麼需要這些變更

- 避免菜單價格只由可修改的前端決定，或將展示用的資料當成真實訂單。
- 維持菜單與旅人訂單的權限隔離，符合最小授權。
- 讓館方調整項目與上架狀態時不必修改前台程式，減少部署及版本不一致風險。
- 對既有資料保留相容性，不因初始資料重新建立而覆寫館方修改。

## 對應版本及未解風險

- 基礎菜單：`supabase/migrations/20261113_01_menu.sql`，並依賴既有管理員／更新時間資料庫函式。
- 多次套用歷史 migration 並不必然安全：相同名稱、不同 ID 的分類可能重複，後續權限也可能改動。正式 schema 與應用版本需另行確認。
- 輸入驗證、防濫用、歷史價格快照及匿名存取界線由 `docs/TEA_ORDER_SETUP.md` 與 `docs/SECURITY_REVIEW_20261117.md` 持續追蹤。
- 靜態自動測試不能證明正式資料庫的 RLS 與提交權限正確。
